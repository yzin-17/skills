# 当前计划、实施日志与证据的文档结构

本规则负责文档内容的归属、更新和迁移。它不改变已确认目标、任务拆分粒度、授权或验收标准；不能因任务数量多、日志长就缩减正确的实施范围，也不能用拆文档替代必要的任务拆分。

## 1. 内容归属

| 文档 | 应维护的内容 | 不应承担的内容 |
| --- | --- | --- |
| Spec | 当前目标、非目标、设计、行为/兼容性约束、AC 与必要决策依据 | 逐轮实施汇报、实际命令输出、完整写集和调试过程 |
| Task | 当前范围和执行计划、稳定任务 ID、依赖、执行边界、完成条件、当前状态、精确阻塞、下一步、最新证据链接 | 历次检查点、不断追加的阶段报告、全量测试日志、失败重试过程 |
| 实施日志 | 按日期和任务 ID 记录发生过的实施批次、方案调整原因、授权事件、交接及结果变化，并引用详细证据 | 第二套当前任务表、另一份活动计划或新的验收标准 |
| 验证/证据报告 | 某个任务或门禁的断言、输入/版本、写集、实际命令或过程、结果、失败与修正、环境及未覆盖范围 | 代替 Task 决定当前任务是否完成，或者只凭历史通过宣称当前仍通过 |
| Review/调研报告 | 较长的审查发现、差异矩阵、分析依据与证据 | 复制 Task 的完整进度表；报告中的待办应指向 Task 中的责任项 |

Task 是当前执行状态的唯一权威入口。顶部摘要是其当前任务和门禁的简短概括，不单独计算另一套进度；日志与报告只保存有日期/基线的观察。最终 Review 沿用原来的单一责任，Task 保留最新结论及未解决问题的责任链接，详细发现可以放在关联报告。

## 2. 路径与按需创建

优先沿用仓库的文档指南和既有日志、证据、Review 路径；不要同时创建一套新的平行目录。无约定时可使用：

```text
docs/specs/YYYY-MM-DD-<task-id>.md       # 稳定契约
docs/tasks/<task-id>.md                 # 当前执行入口
docs/tasks/<task-id>/implementation-log.md
docs/tasks/<task-id>/evidence/<gate-or-topic>.md
```

仅在确有内容需要保留时创建支持文件，不为简单任务生成空日志、空证据目录或空 Review。一份短实施日志可以直接包含简短验证记录；当验证细节较多时再独立成报告，由日志引用，不将同一段结果复制两次。

按有意义的实施批次、门禁或主题组织记录，不按每次工具调用、每个命令、每次重试拆文件。日志持续增长并影响定位时，可以按阶段分卷；Task 链接当前相关卷和必要历史入口，不复制完整卷目录及旧摘要。

## 3. Task 保持可直接执行

Task 顶部维护最近核对时间、当前实施/验收概况、当前执行叶、阻塞或下一可执行叶。涉及权限或并行工作时，补充当前适用的授权边界与资源归属。每次进度变化时原位替换这些内容，不在末尾追加一份“最新状态”。

执行叶沿用 `task-planning.md` 的完整执行包：AC、启动依赖、必要上下文、可写范围与排除项、完成条件、验证方式。这些是尚未履行的执行契约，不能为了缩短文件一起移到历史日志。执行后仅更新最新结果、未满足条件和证据链接；完整实际写集、命令和历次尝试放到支持文件。

共享门禁只在一个权威条目记录当前状态，其他任务引用它。父分组不与子叶重复计数。已完成叶可保留简短结论和证据链接；有恢复、审查或兼容需要的执行契约继续保留。

出现以下情况时应调整文档归属，而不是继续追加：当前状态有多个互相矛盾的版本；同一任务反复记录长命令/写集；阶段汇报掩盖任务定义；必须读到日志末尾才知道下一步。不要按固定行数机械切割，也不要因此新增实施任务或改动产品范围。

## 4. 每次检查点的更新

1. 重新读取待修改的 Task 条目和关联记录，确认没有并行更新。沿用现有写入归属；子执行者只写分配给自己的报告，Task 由指定维护者对账。
2. 将有保留价值的实施事实写入日志或证据报告，绑定日期、任务/AC、代码/工作区和环境。失败及修正仍需可追溯，不能只保留最后一次绿色结果；证据正文只维护一份。
3. 原位更新受影响任务的当前结果、门禁和顶部摘要，并链接本次适用证据。授权的时间、范围及使用/恢复结果写入历史；当前入口保留仍有效的限制，不把已执行完毕的一次授权当作后续授权。
4. 核对状态与证据的适用性、链接以及下一执行叶。输入变化导致旧证据失效时，仅重开受影响任务/门禁；文档搬迁本身不使证据失效，也不使任务完成。

如果记录写入成功但 Task 更新因冲突未完成，明确说明尚未对账，不宣称文档已同步。已记录的历史必须标明当时基线，不能把未核验的旧结论写成当前事实。

恢复或交接时先读 Task 当前摘要、所执行叶和最新证据，再按具体疑问读取历史。新的稳定需求/设计决定回写 Spec，当前执行义务回写 Task；不得只藏在日志或对话里。

### 实施记录示例

```md
## 2026-10-11 / T3 / 缓存隔离验证

- 对应任务：[当前 Task](../<task-id>.md) `T3`；验收断言：AC2
- 当时基线与范围：<代码/未提交工作区、环境与本批变更边界>
- 过程与决定：<必要的失败、修正或边界调整；新增工作注明原 AC、发现的前置/缺陷或明确扩围依据>
- 当次结果与证据：<结果、证据报告相对链接及锚点>
- 当时未覆盖：<仍需验证的层级；当前状态回查 Task>
```

### 证据报告最小内容

```md
# <门禁或主题>验证记录

对应 Task：<相对链接>；任务/门禁：<稳定 ID>；断言：<AC 及具体行为>

## <日期或基线标识>

- 输入：<代码/工作区版本、必要配置与目标运行态；不包含密钥>
- 变更范围：<本次实际写集或可定位的补丁/变更引用>
- 验证：<实际命令/操作、关键断言；标明 fixture、集成、实源、浏览器等层级>
- 结果：<通过/失败/未执行/阻塞/不适用及原因；跳过项不计通过>
- 修正与复验：<出现问题时记录根因和受影响复验，无则省略>
- 证据边界：<未证明的行为或环境；原始日志/产物位置与可用性>
```

临时路径可以作为辅助定位，但不能是完成结论的唯一依据。将必要输入、过程、结果及边界保存在仓库报告或获准的持久产物中；凭据、大型原始日志、业务备份和不应跟踪的生成物不因此进入 Git。证据缺失或已不可访问时明确记录，不补造测试结果。

## 5. 迁移已有杂糅文档

在授权的文档整理范围内增量操作，不顺带重排或裁剪产品计划。

1. 盘点当前 Spec/Task、任务与 AC 标识、勾选、依赖、未解决义务、授权边界，以及实施历史和所有将受影响的链接/锚点；保留写前对照，检查并行修改。
2. 按语义抽取阶段汇报、实际命令/写集、重试、旧检查点和详细证据到日志/报告，保留原日期、任务 ID、结论和适用基线。尚未完成的任务定义、门禁与未决要求留在 Task；混合段落需要分离，而非整段盲移。不要根据过期页头或复选框数量推断当前状态。
3. 从实际证据整理 Task 的唯一当前摘要和受影响条目。纯拆文档不改变勾选或验收含义；如发现状态确有错误，单独标明对账依据，不把状态修正藏在搬迁里。
4. 修复支持文件中的相对链接、回链和所有可找到的入站锚点引用。无法修改的外部引用若仍需要旧锚点，按仓库惯例保留紧凑的显式锚点跳转，不复制历史正文；报告无法修复的引用，不擅自制造另一份活动 Task。
5. 对照迁移前后，核对任务/AC、依赖、授权、未完成义务与证据均未丢失，没有重复责任清单；验证链接，并确认读者不打开完整日志也能找到当前边界与下一步。

将历史拆到支持文件不等于归档 Task。完成后的 Task 仍按 `archive-handling.md` 独立判断能否归档；支持文件可随 Task 搬迁并修复双向链接，或保留稳定位置，跨任务共享证据不重复复制。
